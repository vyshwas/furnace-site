Findings

F1 · High (Critical if post ids are ever visible to others) · Confirmed

Anyone with a post's id, signed in or not, can delete or rewrite it

Where
The post API's delete and update handlers, through the shared "does this user own this post?" helper.
What happens
The helper counts posts matching the post's id and the signed-in user's id. With nobody signed in, the user id is undefined, and Prisma leaves out a filter whose value is undefined. The check then matches the post by its id alone and says "yes". So a request with no login can delete any post, or replace its title and content. The attacker needs the post's id. Ids are long random strings, so they are hard to guess, but they show up in links, browser history, screenshots and logs. An id is not a password, and the code treats it as one.
How I checked
Read the handlers and the helper. A signed-in user asking for another user's post is refused correctly (the filter uses their own id and finds nothing); only the signed-out case slips through. Prisma's documented behaviour for undefined in a filter is to ignore that field.
Fix
Refuse when there is no session, before the query, and use the non-optional id. Both handlers already turn false into a 403.
async function verifyAccess(postId: string) {
  const session = await getServerSession(authOptions)
  if (!session?.user?.id) return false
  const count = await db.post.count({
    where: { id: postId, authorId: session.user.id },
  })
  return count > 0
}
Check it's fixed
Signed out, send a delete request for a real post id: it must answer 403 and the post must still exist. Signed in as another user: also 403.

Worth improving (does not block launch)

I1. No security headers in the code or host config · Medium

The Next.js config sets none. Your host may add some; check the live site's response headers. Add Strict-Transport-Security, X-Content-Type-Options, X-Frame-Options and Referrer-Policy in the config's headers() (Furnace's report has the code).

I2. No rate limit on the post write endpoints · Low once F1 is fixed

After the fix they need a login. Before it they are open to everyone, which makes F1 worse: a script could empty the posts table quickly.

I3. No rate limit on the billing endpoint · Low

It needs a login and creates a Stripe checkout or billing-portal session per call. Stripe sessions cost nothing, but a signed-in script can create many; a per-user limit (10 a minute) is enough.
